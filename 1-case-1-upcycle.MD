In our PostgreSQL/PostGIS database, we currently implement a query with a shape like that found in the file 2-current-query-shape.md.  This query feeds aggregated spatial data to a map tile server and web map frontend.  This query references raw data tables, and performs several CPU and mem expensive joins.  The task described here will refactor the query architecture to create a new schema with several materialized views that reference this raw data and produce pre-joined tables and aggregate values.  This will allow for much more efficient service.  The schema should be called organization_aggregates  The outputs of this task with be Postgres DDL to create materialized views and DAGs for Apache Airflow to refresh these views every 6 hours. The materialized views will be defined below.  Also create appropriate indexes on these views.  Create a plan for claude code to implement the outputs and report it before proceeding with the implementation.  Claude code will implement the outputs, generate a cost and environmental impact estimate using our established criteria (reference ecologicts in statusline for environmental impacts: carbon footprint, water footprint, and energy).  Ask me any relevant questions to fill in gaps before producing the plan.

Materialized Views
(1) The first CTE in the current query shape generates a table capturing the parent-child relationship between organizations.  Create a materialized view that generalizes this for all orgs and can be used in joins.  Some work as already been done on this and is found in 3-organization-children-view.sql.  Check this view and suggest any improvements.  In a complex query this view will be filtered by map_name or parent_id columns.  Call this materialized view organization_hierarchy.

(2) The second CTE in the current query shape identifies the planting organization id from two possible sources for each tree: (a) the organization id of the associated planter, or (b) the planting_organization_id assigned directly to the tree.  planting_organization_id on the tree record takes priority.  Create a materialized view that generalizes this for all trees in the database so we can filter directly on map_name, organization_id, or top level parent_id.  Top level parent_id will be loaded from materialized view (1) after it is built/refreshed.  Also include all columns from the trees table that referened as SELECT outputs in the rest of the current query shape, so that the trees table does not need to itself be joined in the live query. Call this materialied view organization_trees.

(3) Finally, create a materialized view that calculates the per-organization cluster records in advance, rather than on demand.  This must include cluster totals and centroid for every zoom level, just like the outputs of select statements inside the current query shape.  Note that the current query shape queries clusters twice: once to find the matching clusters, and then again on higher zoom level to identify the zoom target of that cluster.  Do not combine these two queries in materialized view 3, they will be joined later in the live query.  The cluster in the zoom target query with the highest tree count with a centroid within the region of the lower zoom level cluster takes priority.   This materialized view must expose all coluanms the current query shape exposes.  This materialized view will be filtered organization id or top level parent organization, and then by zoom level and a match between centroid and a spatial envelope.   Call this materialized view organization_clusters.
